# Reviewed meeting invitations

Implementation and mock tests do not establish production deployment, real invitation delivery or recipient agreement.

Start with a reviewed candidate from `協調會面：日期、時間、時區、長度`. Before creating a private hold, prepare an external invitation with `準備會面邀請 <candidate-code>：alice@example.org,bob@example.org；地點：台北辦公室`. Explicit email addresses are required; no AI-selected attendee list or same-name contact inference. An existing private hold can use the same preparation command; its preview explicitly states that the original event will be converted. Separate confirmation is still required.

The private preview displays every attendee, title, start/end/timezone and location. Confirm with `確認會面邀請 <invite-code>` within fifteen minutes. Preparation is local. Confirmation rechecks the source thread, account/calendar binding, contact preferences and configured-calendar availability; a durable claim precedes the provider write. Guest calendars remain unverified. The invitation uses a deterministic event ID, immutable reviewed fields and `sendUpdates=all`. Guests cannot edit/invite others, and their guest list is hidden by default. Calendar acceptance is not proof of email delivery.

`查看會面邀請` or `查看會面狀態` reads the event and verifies its identity, ownership, exact attendees and content. An organizer event status of confirmed does not establish attendee acceptance. Every requested attendee must be present and accepted, with organizer status confirmed, before all-accepted is reported. Declined, tentative, missing or omitted RSVP information remains declined/pending/unverified. This is a point-in-time observation, not a guarantee against later changes.

`取消會面邀請準備 <code>` abandons a local invite/cancellation review. It does not recall an operation already started. For a submitted invitation, use `準備取消會面邀請 <candidate-code>` and review its event/guest list, then `確認取消會面邀請 <cancel-code>`. Cancellation rechecks the owned event and uses its ETag, with notifications to all invited guests. Only the provider's expected cancellation acknowledgement establishes cancellation. Changed guests/content are not silently cancelled.

Unknown create/delete outcomes are not replayed. Read-only reconciliation can recover a matching created event. An unresolved cancellation requires further reconciliation; it is never reset to an automatic retry. Definite API rejections require fresh review. No tests send to real contacts or modify real calendars.

Submitted invitations are registered before the provider write and checked by the existing mail scheduler, including runs where the day's mail digest was already completed. A meaningful observed RSVP change sends one timestamped owner-only update. Unchanged evidence sends nothing; recurring transitions use separate durable revisions. Read failures disclose that the latest status is unverified and suppress stale updates. Definite Telegram rejection may retry; uncertain notification outcomes never replay automatically. The active registry is bounded at 100 entries and only known inactive index entries can be removed; this does not delete the underlying event or meeting state. Each polling run verifies the Calendar owner once and has a 45-second provider-wait budget with a durable rotating cursor, so slow records do not starve later invitations or indefinitely delay the mail digest. Private operational counts/cursor are stored in meeting-rsvp-health; per-revision delivery journals retain the actual send/uncertain/retry outcome. This is polling at the existing scheduler cadence, not a real-time webhook or an external chaser.

Conversion uses conditional PATCH with the original ETag and sendUpdates=all, preserving the same event ID. It refuses changed/recurring holds, additional descriptions, locations, attachments, conference data, shared properties and unknown fields instead of publishing or deleting unreviewed private content. Fresh complete agenda checks exclude only the exact owned hold on its source calendar; another overlapping event still blocks conversion. Abandoning review or a definite provider rejection restores the held state. Unknown PATCH outcomes remain uncertain and are never automatically repeated. Holds created before calendar-account binding was recorded require manual reconciliation and cannot be converted by this workflow.

Remaining coordination work: rescheduling, negotiation based on reply content, and conference-link creation. This phase does not claim these capabilities.

Official contracts: [events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [event resource and attendee response status](https://developers.google.com/workspace/calendar/api/v3/reference/events).

Reply drafts for the same mail card bind to a minimal related-meeting snapshot. Meaningful meeting changes invalidate draft saving or sending; polling timestamps and notification bookkeeping do not. Draft generation receives only user-relevant meeting details, without internal confirmation codes. Before sending, owned Calendar event evidence is rechecked after native Gmail draft inspection, followed by an atomic local meeting-state check. Unknown Calendar reads stop mail submission. These checks are observations at that time, not a distributed transaction across Gmail and Calendar; unrelated conversations are not inferred or linked.
