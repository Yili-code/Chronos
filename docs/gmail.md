# Gmail → Telegram → Chronos tasks

此功能需要 Chronos 自己的 Google OAuth 授權；ChatGPT/Codex Gmail 外掛的登入與權限不會自動傳給 Chronos。預設關閉，尚未授權或部署時不會處理信件。

## 已實作的行為

### 第一層篩選

新建立的每日批次預設使用 `CHRONOS_GMAIL_FIRST_LAYER_SCREENING=true`：先判斷是否值得通知，再決定呈現方式。

- **重要信**：確實需要本人採取具體行動才個別通知。卡片固定列出具體重點、需要做的事、原文明確期限及實際欠缺的決策資訊，不展示內部分類理由。
- **一般資訊**：系統狀態／完成通知、收據、不需處置的帳號通知、電子報與可選活動合併為分組摘要。沒有退訂標記、往返信或保護關鍵字，都不等於需要逐封通知。標題可直接開啟原信，內文保留具體結果與事件資訊。
- **明確低價值群發信**：自動封存，彙整列出主旨、理由及原信連結。只移除 INBOX，保留已讀／未讀狀態，不移到垃圾桶。
- **需要確認**：只有真正需要本人選擇或確認的具體問題才個別通知，卡片必須說明問題與可用事實。純文字／HTML 呈現不同、有附件或部分內文未讀，不直接變成待判斷。分類服務暫時失敗時保留批次進度並回報可重試失敗，不推送原文碎片或重複的保守卡片。

星號、重要、私人分類、白名單、使用者保留、已有任務、往返信、附件及帳單／安全／作業等內容受保護。實習、開源、創業、補助、獎學金與競賽等機會不會因為群發就自動封存。封存還需要退訂標記、Gmail 群發分類、足夠分類信心、沒有明確下一步，並在實際操作前重新讀信核對保護狀態。這是保守的可回復整理，不保證零誤判，也不代表已查證活動資格。

上述保護只限制自動封存，不決定通知優先度。受保護但不需行動的通知仍可進摘要。AI 會讀取可見正文與另一呈現版本、附件清單與讀取限制，擷取有依據的日期、結果、金額、條件等資訊；不會推測未讀附件內容或把「請查看原信」當成具體待辦。資訊不足以完成分類時屬於系統待重試工作，而不是要求使用者判讀技術警語。

每日模式不再套用下方舊促銷／安全通知自動移垃圾桶規則；`/mail_next` 歷史整理仍沿用既有五封互動流程。設為 `false` 可為新批次恢復舊每日模式；已開始的批次固定沿用原模式，以免重試時混用行為。部署前既有的未完成批次也沿用舊模式。

分類及封存進度會保存；封存結果不明時，重試先讀 Gmail 狀態。摘要按長度分頁，逐頁保存送達紀錄；結果不明的 Telegram 投遞不自動重送，也不推進完成游標。已封存郵件可由摘要連結開啟，再於 Gmail 移回收件匣。分類不會自動新增任務、寄信或代為報名。

郵件彙整是可回頭閱讀的參考內容，會保留在 Telegram，不套用一般完成通知的七秒自動刪除。彙整不因此變成需要回覆的郵件，也不會將來源信標為已讀或新增待辦；一般操作完成通知仍沿用原本的七秒規則。

下列逐封播報及自動垃圾桶行為描述的是舊每日模式與歷史整理；第一層篩選模式以上述規則為準。

- 每天 **Asia/Taipei（UTC+8）07:00**，通知上次成功掃描後新增的郵件，含已讀與未讀，但排除寄件備份、草稿、垃圾桶與垃圾郵件。使用 Gmail 秒數時間範圍查詢（[官方說明](https://developers.google.com/workspace/gmail/api/guides/filtering)），每封成功播報一次。首次沒有時間紀錄時，只取前 24 小時的新信；歷史郵件仍由 `/mail_next` 整理。每次預設最多 100 封，達上限時保留原起點，後續執行跳過已播報項目並接續處理。只有完整批次成功後才推進掃描時間；不會更動保留郵件的已讀狀態。沒有新信時不傳通知。
- 僅同時符合 Gmail `CATEGORY_PROMOTIONS`、`List-Unsubscribe` 與明確促銷詞的信移到垃圾桶。帳單、交易、登入、安全、作業／工作等關鍵字、往返信、星號、重要郵件、私人分類、白名單，以及內容過長而無法完整檢查的信保留。這是保守啟發式，不是完美分類；可先檢視預覽、加入白名單。
- Telegram 逐封簡短回報移到垃圾桶的主旨、寄件者及原因；其他信提供繁體中文摘要、建議下一步與 Gmail 連結。摘要使用既有 Gemini，失敗時顯示原文摘錄。不會開啟郵件內連結或自動讀取附件；擁有者可在原卡片明確要求[附件清單與受限文字預覽](mail-correspondence.md)。
- 直接按郵件卡片按鈕或回覆 `刪除`、`保留`、`已讀`、`新增任務：要做的事`。使用現有 Telegram webhook 立即處理，不等隔天。
- 新增任務必須由使用者要求。每封信最多建立一個 task，保留原信連結；重複點擊、Telegram 重送與併發更新不會重複建立。後續修改沿用 `/edit`。
- 支援[完整郵件串回覆草擬與回覆追蹤](mail-correspondence.md)。保存 Gmail 草稿不會寄送；只有透過[獨立的逐封寄送確認](authorized-mail-send.md)，核對收件者、主旨與正文後，才會提交寄送。單獨回覆「寄出」不會寄信。沒有轉寄或永久刪除入口；OAuth 權限不是逐封寄送許可。
- 目前只支援既有的私人 Telegram chat（正數 chat ID），且必須設定 webhook secret。群組使用尚未支援。

## 第一次授權

1. 在 [Google Cloud Console](https://console.cloud.google.com/) 選擇自己的 project，啟用 **Gmail API**。
2. 在 **Google Auth Platform** 設定應用名稱與聯絡 email；Audience 使用 External，Testing 階段把自己的 Gmail 加入 test users。
3. Clients → Create client → **Desktop app**。下載 client JSON，放到本專案 `.gmail/client.json`。`.gmail/` 已排除 Git 與 Cloud Build，請勿貼 JSON 或 token 到聊天。
4. 在專案根目錄執行：

```powershell
New-Item -ItemType Directory -Force .gmail | Out-Null
.\.venv\Scripts\python.exe -m chronos.gmail_authorize --client-secret .gmail/client.json --account YOUR_EMAIL@gmail.com
```

瀏覽器會開啟 Google 同意頁。確認正確帳號並授權後，工具會用 PKCE 與隨機 state 驗證本機回呼，再確認 Gmail 帳號符合 `--account`。client ID、secret、refresh token 與帳號存入 `.env`；不會輸出憑證、不會改信、不會開啟郵件功能。Google 同意或重新登入必須由帳號持有人完成。

Gmail 的垃圾桶 API 需要 `gmail.modify`。該 Google scope 也涵蓋寄信能力，**Google 沒有在此 scope 內拆出「寄信前詢問」**；本程式透過 owner/card 綁定、逐封內容審查、獨立確認與不確定結果禁止重播限制行為。不要將此 OAuth token 用於未受控的其他程式。參考 [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)、[trash](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/trash)、[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)。

External + Testing 的 refresh token 可能有短期有效期限；長期運作前依 Google 對應用發布狀態與帳號的規定完成設定。授權失效時會停止處理，須重新授權，不會退回其他帳號。

## 預覽與本機啟用

先用唯讀預覽查看會被過濾的信（輸出包含主旨和寄件者，勿公開分享）：

```powershell
.\.venv\Scripts\python.exe -m chronos.run_mail
```

在 `.env` 補好既有 Telegram/Gemini 設定，需要時加入白名單：

```dotenv
CHRONOS_GMAIL_KEEP_SENDERS=person@example.com,@company.example
CHRONOS_GMAIL_MAX_MESSAGES=100
CHRONOS_ENABLE_GMAIL=true
```

重啟 Chronos。啟用內建 scheduler 時，服務必須在 07:00 持續運行；排程以 Asia/Taipei 固定。若 07:00 未運行，當日不會自行補跑。

## Cloud Run

完成本機 OAuth 後，使用原部署腳本加上明確旗標：

```powershell
pwsh -File .\scripts\deploy_cloud_run.ps1 -ProjectId YOUR_PROJECT_ID -EnableGmail
```

Gmail 憑證由 Secret Manager 注入，不放進 image。郵件使用獨立的每天 07:00、Asia/Taipei `/internal/mail/daily` Cloud Scheduler job；待辦仍使用 08:00 的 `/internal/daily`，不再觸發郵件通知。內建 scheduler 在 Cloud Run 保持關閉。每次需要啟用 Gmail 的部署都要帶 `-EnableGmail`；省略會關閉功能。部署是獨立步驟，新增程式碼或通過本機測試不代表 production 已更新。

## 資料與失敗處理

SQLite 的 `mail_state` 或 Firestore 的 `<prefix>_mail_state` 保存郵件 ID、主旨、寄件者、日期、最多 12,000 字元內文、摘要、原卡片對應與任務／投遞紀錄。這些資料目前不自動到期；資料庫備份亦包含郵件資料。Gemini 會收到摘要或任務解析所需的郵件文字；Telegram 收到主旨、寄件者與摘要／摘錄。

啟用 correspondence 工作流程後，另保存本機草稿、最多 4,000 字元的必要 owner 要求／補充上下文、原郵件串雜湊、確認與寄送狀態。草擬或會面解析會把所需郵件串送給既有 Gemini；不會把其他聯絡人的資料當作工具權限。補充提示的版本保存在原始 receipt，避免延遲投遞錯綁新要求。

垃圾桶操作前先保存待處理紀錄；Gmail 寫入結果不明時，下次先重新讀取狀態，必要時重試同一個可重複操作。未完成的批次會跨日接續，避免已移到垃圾桶的信漏報。

Telegram 傳送前也保存紀錄。遇到 timeout 或服務錯誤而無法確定投遞結果時，批次回傳 503 並保留 `sending/uncertain`，**不盲目重送或聲稱完成**。管理者須檢查 Telegram 和資料庫紀錄後才能修復投遞狀態；目前沒有自動解除不明狀態的介面。明確拒絕（例如 HTTP 429）可於後续排程重試。OAuth／Telegram 配置錯誤會保留進度並回報失敗。

`保留` 防止這封信以後被自動過濾，不代表從垃圾桶還原。已在垃圾桶的信可直接在 Gmail 還原。


## 歷史收件匣每批五封

管理者可用既有 scheduler secret 呼叫 POST `/internal/mail/backlog` 啟動，或由擁有者在 Telegram 傳 `/mail_next`。
每批最多五封，涵蓋啟動當時收件匣內已讀及未讀郵件，依 Gmail 列表順序整理，不把批次冒充實際日期。
保守自動過濾仍僅適用未讀促銷；已讀信交由使用者決定。卡片「保留（封存）」或回覆「封存」只移除 INBOX，原信可在所有郵件找到。
新增任務或標為已讀不會封存。Read 會結束該信的整理並移除 Telegram 卡片，信仍留在收件匣且不再列入後續批次。當本批郵件全數處理後，傳 `/mail_next` 取得下一批；未處理完會提示剩餘數量。
歷史整理的每批五封與待處理關卡只適用 `/mail_next`；每日新信通知獨立執行，不會被歷史整理阻擋。
批次、截止範圍及指令識別保存在資料庫；重送同一指令不會多開一批。不寄信、不永久刪除。

## 唯讀搜尋

傳送 `/mail_search from:client@example.org subject:報價` 或 `搜尋郵件：from:client@example.org subject:報價`。冒號後是你提供的 Gmail 查詢，支援寄件者、主旨、日期及標籤等 Gmail 搜尋語法，不自動翻譯自然語言為查詢，也不從顯示名稱猜測 Email。查詢需 1 至 500 字元、單行、非空白。

每頁最多五封，列出原文節錄與 Gmail 連結；還有結果時提供 `/mail_search_next <code>`。分頁綁定目前帳號與擁有者，有效 15 分鐘；取得新一頁後舊碼失效。查詢結果是讀取當時的快照，郵件新增或刪除可改變分頁結果。`in:anywhere`、`in:trash`、`in:spam` 明確要求時才包含垃圾桶／垃圾郵件。

搜尋不會分類、標已讀、封存、刪除、寄信或自動建立草稿／追蹤。回覆選定結果卡片後，可沿用既有草擬、聯絡人與會面流程。中途讀取失敗不呈現部分結果，也不宣稱沒有符合郵件；同一 Telegram update 重送從已確認投遞的位置繼續，不重新搜尋。遠端送達後、本機 receipt 保存前中斷仍可能重複卡片，並非 exactly-once 保證。

使用官方 [users.messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) 與逐封讀取；沿用已授權 Gmail 帳號，不新增 OAuth scope。

## 自然語言本機流程

綁定郵件卡片後，也可用「照上一封討論的條件婉拒，不要透露底價」等隱含草擬要求。保密、語氣與內容限制會保留在模型收到的完整要求中；「不要回覆／不用追蹤」等操作否定仍會停止準備。若沒有選定郵件，會先要求選卡片，不猜測「他」是哪一位。

當明確承諾與未決定訊號同時出現時，系統會額外核對相關決策是否一致。對同一項事實同時承諾又表示未決定，會先詢問擁有者；不同事實（如價格已確認、交期仍未定）可分別保留其狀態。核對失敗不建立新草稿、不覆寫原草稿。這是針對可辨識高風險訊號的檢查，並非所有語意矛盾的完整驗收保證。

回覆綁定的郵件卡片，例如「幫我草擬英文回覆，並在 3 天後提醒我追蹤」。支援本機回覆草稿、一個會面候選時間、明確間隔的追蹤，或一起準備。搜尋結果卡片也可使用，例如「幫我協調會面：後天下午三點、台北、1 小時，草擬英文回覆提出候選時間，3 天後提醒我追蹤」。會面長度與追蹤間隔用逗號或分號分開；追蹤間隔使用阿拉伯數字、單一小時或天數（1 小時至 90 天）。可明確提供一位郵件串內的追蹤對象 Email。

所有步驟會一起套用。任一步需要補資料、狀態變更、郵件串更新或超出完整預覽上限時，整個流程不套用。會面空檔在草擬完成後重新核對；草稿綁定同一份候選資料。定時候選在儲存或寄送草稿前也重新檢查，過期、撞期或讀取失敗不會寄出舊提案。草稿尚未寄出時，收到對方來信的郵件串仍標示「等你回覆」，不把本機草稿當成已送達。追蹤只提醒擁有者一次，不寄催覆郵件。

「這個時間方便嗎？」是草稿正文中問收件者的問題，不是要求擁有者先替對方確認空檔。只有缺少必要事實時才停止等待擁有者補資料。模型服務逾時或暫時不可用會明確回報，保留既有會面候選；不把服務錯誤當成日期不完整，也不覆寫成待補資料。

Gmail 草稿儲存、實際寄送、收件者變更、附件、Calendar 活動建立／邀請與搜尋操作需使用各自確認流程；自然語言規劃不會產生授權。組合操作僅準備本機會面候選，不建立活動、不暫留、不邀請對方，也不代表對方有空或已同意。已有暫留／已送出邀請須先核對，不能以新候選覆蓋。條件式未來寄送後追蹤、重複提醒、含混間隔與矛盾要求會先釐清；請用完整要求重提。未綁定郵件卡片的郵件要求會要求先選定卡片。仍須先搜尋並選定結果，並非自動選人或任意跨功能指令的完整支援。

## 帳號安全通知規則

`CHRONOS_GMAIL_DISCARD_ACCOUNT_SECURITY_AFTER` 是使用者啟用規則的 Unix 秒數，預設 0 關閉。僅處理 Gmail 收件時間不早於此時間的未讀安全通知（新裝置／異常登入／密碼已變更等主旨），移到垃圾桶並回報原因。既有歷史郵件不受影響；白名單、星號、往返信與套件漏洞通知仍保留。依既有整理排程執行，不是即時 Gmail 規則。

點選 Trash、Archive、Read 或回覆對應指令後，Gmail 操作成功才會移除原 Telegram 卡片。刪除卡片失敗可重試，不重複執行 Gmail 操作。

Task 按鈕先顯示 `Read email:〈主旨〉` 與 Yes／Edit／Cancel；Yes 才建立待辦，Edit 可回覆自訂標題後重新確認，Cancel 不建立。按 Trash 成功只移除卡片，不另發成功確認訊息。

### Existing draft freshness

「查看回覆草稿」或「用剛剛那份草稿回覆」會在顯示本機待確認內容前重新核對郵件串、會面狀態與24小時有效期。失效時不顯示舊正文，必須依最新內容重新草擬；這些要求本身不授權儲存或寄送。核對失敗時保留原狀並停止。已開始儲存／寄送或結果不確定的草稿只顯示既有操作狀態，不重試外部操作。

### Natural draft save and recipient boundaries

回覆已展示的最新版草稿「存成 Gmail 草稿就好」可使用該預覽綁定的版本授權儲存，不授權寄送。回覆原郵件卡片或缺少版本時，只顯示經重新核對的草稿供確認；不會直接建立 Gmail 草稿。舊版本、待補資料或失效草稿不能儲存。Gmail 接受後若回覆逾時，狀態保持不確定，不自動重試。

Reply All 複合要求會核對最新郵件中的已知 To／CC，要求新增 To／CC／BCC 的確切 Email，不依職稱猜測。向外加入或轉寄附件仍未支援，敏感檔案的揭露範圍與授權需另行核對；這類複合要求不讀取檔案、不改寫草稿、不寄送。可在 Gmail 手動完成附件流程。

### Qualified named replies

「回給 Alex，公司那位，不是學校那位」會先比對明確維護的本機姓名、公司／職稱欄位與正反限定，再核對目前郵件的已知寄件地址。公司／學校等分類只使用欄位中已有的明確關係標記，不依網域、顯示名稱、郵件內文或模型猜測。其他公司／職稱限定需完整欄位吻合；資料不足或多個候選時先確認，不自行合併或換郵件串。這是本機資料與來源的核對，不代表外部身份驗證。

目前這類指名要求先完成對象核對並要求補充草擬內容，不會將身份限定當成回覆正文，也不會自動儲存或寄送。來源卡片不符、聯絡人不主動聯絡，或準備後資料／帳號變更時停止。

### Search, draft and monitor

支援有界的複合要求，例如「找出報價信，草擬回覆並追蹤，但先不要寄」。目前依明確主旨文字搜尋，必須只有一個結果且無下一頁；不猜哪封。一般草稿採不代表接受條件的中性確認收件方式，有必要立場問題則保留給使用者。未指定間隔時只監測回覆狀態，不排定提醒；可明確加上「追蹤 3 天」。自訂內容與進階條件請先透過 /mail_search 選擇卡片再處理，不會忽略未支援的子句。

搜尋來源、草稿與追蹤使用單次原子保存；來源或本機狀態在準備期間變更、任一步驟失敗、預覽過長、已有未完成追蹤時，整個流程不套用。儲存至 Gmail 仍需點選實際預覽版本的確認控制，不會寄送。投遞失敗可重播同一更新，不再搜尋或生成。單純「幫我回覆這封信」先讀完整脈絡再確認缺少的回覆事實，不在讀信前要求使用者重述內容。

複合搜尋僅在搜尋子句有明確郵件用語時進入此流程。一般市場研究、報告草擬與進度追蹤不會只因同時包含「搜尋／草擬／追蹤」而被保留為郵件要求；未綁定卡片的一般訊息仍使用原有任務分派。

可參加的活動／競賽等項目即使不是必須處理，也會提供獨立郵件卡片與「加入安排」按鈕；按鈕綁定原信，採用既有時段核對與衝突處理，不會自動報名或邀請他人。一般通知、電子報、產品與服務消息、過期資訊分別推送，不跨類別混頁；每頁保留類別與日期，普通資訊使用短摘要。
