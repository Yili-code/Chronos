# Telegram 訊息保留規則

YiLi 的偏好是：所有不需要回覆或完成待確認操作的 Chronos 訊息，成功送出七秒後自動刪除。這是共用發送層的預設，不是郵件、課程或幾句固定文案的特例。包含課程進度回執（今天無課、沒有進度或已完成）、操作結果、排程成功、摘要、唯讀報告、提醒與文件訊息。刪除的只有 Telegram 訊息，不影響任務、郵件、Calendar、進度紀錄或已保存的文件。

需要回報進度、補充資料、確認或選擇的訊息保留。單純提供調整時間、復原、檢視或網址入口，不表示必須回覆。已知通知來源明確傳入 `requires_response=False`；互動來源使用 `requires_response=True`。未指定時依 force-reply、必要選擇按鈕與純文字追問判斷；新增或模稜兩可的互動必須明確標示用途。既有 `delete_after_seconds=7` 是同一生命週期的相容提示。

`TelegramClient` 在收到成功回應及真實 message ID 後保存七秒期限並啟動計時，立即將發送結果交回呼叫端，讓回執與訊息綁定先保存。HTTP 通知流程與排程工作結束時會等待計時器，避免 Cloud Run 在回應結束後暫停 CPU。SQLite／Firestore 保存待清理訊息編號與期限；中斷或暫時刪除失敗由後續通知請求或工作重試，不重發已送達內容。儲存暫時失敗時使用程序內清理，不把成功發送誤判為失敗。

訊息被改為需要回覆時會取消原期限；處理完的舊按鈕被清掉後可開始期限。健康與狀態 GET 檢查保持唯讀，不因查看服務狀態而刪除聊天訊息。既有已保存的待清理期限可相容恢復；沒有訊息編號的歷史內容不猜測、不批次刪除。

七秒是排定刪除時間，程序中斷、Telegram 拒絕或網路問題可能使實際刪除延後。測試計時器不等於實機 Telegram 投遞／刪除驗證。此規則屬於 Chronos，不改動 Sisyphus 或其他機器人的訊息政策。
